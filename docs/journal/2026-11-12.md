### Car-select FPS (GPU) + GT3 deko lesson

Owner: splash/loading smoother on GPU build; car select ~0.5–1 FPS. Soft too slow to reach it.
Cause: WritebackDk `dkQueueWaitIdle` + full tex-cache drop on every GIF packet (UI = many TEX0 binds).
GT3-revisited [v0.6.0-deko](https://github.com/tomplayer07/GT3-revisited-switch/releases/tag/v0.6.0-deko) is a
native engine (not GS writeback), but the useful pattern is the same: keep textures GPU-resident, batch uploads,
fence/ring instead of idle-per-draw (`texture_upload_batch`, submission slots).

Applied here:
- Invalidate decoded/GPU tex cache only when `TransferCommits` / `ImageQwords` advance (real BITBLT/IMAGE).
- 16-slot pitch-linear texture ring; `WaitIdle` only when reclaiming a slot still in flight, or on SLM flush.
- No idle when EndFrame has nothing dirty to read back.
- Rebuilt/exported soft + `export/switch-gpu/` for device retest of car select.

### Run 2 (CoreGS on): split splash, 5-23 FPS; display and GPU drawer correctness fixes

Owner run 2 logs (`private/switch-device-logs/2026-11-12-run2-coregs-on/`): CoreGS active, sound works, splash shows
the logo on top and garbage below. Average per guest frame: CPU fallback draw 25.7 ms, compose 19.2 ms (fixed cost),
EE 11.6 ms, GPU draw 7.5 ms, GIF 5.5 ms, IOP 3.8 ms, flush 3.7 ms; 3D scenes 4-5 FPS with CPU fallback 90 ms.

Causes found (Confirmed from source):
- SetGsCrt never reached CoreGS: the donor only records the mode, so SMODE1/SMODE2 stayed 0 and the display read a
  full-height frame from a field-mode buffer (bottom half = unrelated VRAM). New `switch/tools/patch-hw-crt.py`
  forwards the syscall; `coregs_set_crt` posts the same SMODE1/SYNCV/SMODE2 words as the PC
  `gs_stream::map_set_gs_crt`.
- WritebackDk accepted every batch and ignored depth, alpha test, the GS blend equation (0x80 = 1.0), TFX, fog,
  wrap modes, lines and points; culled back faces; shared one texture descriptor across all queued draws; decoded
  16-bit textures as 32-bit; seeded the GPU copy only for the first batch's rectangle; discarded pending GPU pixels on
  a CPU fallback; and EndFrame's last batch was drawn after the write-back.
- Fixes: exact-subset acceptance (counted per reason, `[hw-dk] CPU fallback reasons` in stderr.log), per-slot
  descriptors and eight samplers, dual-source blend (As/128) and FIX blend constant, modulate/decal scaling, alpha
  test in the shader, flat shading, STQ, CT16/CT24 texel expansion with TEXA, no culling, half-pixel centre, seed
  growth with write-back, and two optional cpuref hooks (local memory access before transfers, memory sync before
  compose and FIFO reads) so GPU pixels are written back exactly when SLM is read or overwritten.
- Expect: correct splash and menus; 3D still CPU-drawn (depth writes) until the GPU depth path lands.

## Switch run 3 (SMODE fixed) and the full GPU draw pipeline

Run 3 (owner, device; logs in `private/switch-device-logs/2026-11-12-run3-smode-fixed`): the split splash is gone,
480i interlace is back (expected: the game boots in field mode). Rendering is still slow: gs_cpu_draw 37-107 ms per
frame, compose about 11 ms, EE 6-25 ms, 6-18 FPS. The GPU drew almost nothing because the old acceptance rules sent
every depth-tested batch to the CPU.

Changes (built, not yet run on device):
- WritebackDk now owns a GPU depth surface (ZF32) seeded from and written back to Z32/Z24/Z16/Z16S, with ZTST
  NEVER/ALWAYS/GEQUAL/GREATER and ZMSK; depth is written back lazily (the display compose only needs colour).
- The fragment shader covers the GS colour path in integer maths: TFX modulate/decal/highlight/highlight2 with TCC,
  fog, all ATST modes with AFAIL (a second pass for FB_ONLY, ZB_ONLY and RGB_ONLY), FBA, and the wrap modes
  REPEAT/CLAMP/REGION_CLAMP/REGION_REPEAT. Blend `((A-B)*C>>7)+D` maps to GPU factors (As via dual-source, FIX via
  the blend constant). Lines and points are drawn; mipmapped batches use the base level (approximation).
- A start-up self-test draws into scratch memory to pick the y direction and to prove the depth path; if the depth
  check fails, depth batches stay on the CPU and stderr.log says so.
- Still on the CPU (counted per reason): DATE, PABE, blend with C = Ad, COLCLAMP off, 16-bit frame buffers.
- stderr.log repeats `[hw-dk] CPU fallback reasons` every 600 frames so an aborted session keeps them.
